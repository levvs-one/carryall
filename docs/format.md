# Формат комплекта Handinpack

Справочник формата версии 1. Одни и те же описи используются в обычной папке и ZIP. Инструкции для приложения находятся в [руководстве пользователя](how-to-use.md).

## Состав

В корне комплекта находятся два служебных файла:

- `handinpack.json` - машинная опись в UTF-8: состав, относительные пути, длины и SHA-256.
- `contents.txt` - читаемая опись в UTF-8 без BOM, с переводами строк LF. Содержит итоговый путь, относительное имя исходника, число байт и SHA-256 каждого включённого файла; ниже перечислены исключения с причинами.

Остальное содержимое - включённые файлы под выбранными относительными путями. В ZIP нет отдельных записей пустых папок. При записи в папку создаются только каталоги, необходимые для файлов.

Имена `handinpack.json` и `contents.txt` в корне зарезервированы, в том числе как первые сегменты вложенного пути. Например, пользовательский `contents.txt/notes.txt` не допускается. Файл `documents/contents.txt` допустим.

## Машинная опись

JSON использует точные имена свойств в `camelCase`. Неизвестные свойства, повторяющиеся свойства и отсутствующие обязательные параметры отклоняются. Глубина JSON ограничена 16 уровнями.

| Поле | Тип | Значение |
| --- | --- | --- |
| `schemaVersion` | целое число | Только `1`. |
| `createdUtc` | строка даты и времени с часовым смещением | Момент создания описи. Приложение записывает UTC. Поле не удостоверяет время и не участвует в установлении автора. |
| `files` | массив объектов | От 1 до 100 000 включённых файлов, с дополнительными ограничениями ниже. |
| `exclusions` | массив объектов | От 0 до 100 000 записей исключения. Обязателен, даже когда пуст. |
| `contentsLength` | целое 64-битное число | Длина точных байт `contents.txt`, от 0 до 16 777 216. |
| `contentsSha256` | строка | SHA-256 точных байт `contents.txt`, 64 шестнадцатеричных символа. |

Элемент `files`:

| Поле | Тип | Значение |
| --- | --- | --- |
| `sourceRelativePath` | строка | Относительное имя источника, включающее метку добавленной папки, если источник добавлен папкой. Не абсолютный путь машины отправителя. |
| `archivePath` | строка | Относительный путь записанной копии, разделитель `/`. |
| `length` | целое 64-битное число | Число байт файла до сжатия. Ноль допустим. |
| `sha256` | строка | SHA-256 этих байт, 64 шестнадцатеричных символа. |

Например, запись для пустого файла:

```json
{
  "sourceRelativePath": "empty.txt",
  "archivePath": "empty.txt",
  "length": 0,
  "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
}
```

Это один элемент `files`, не полная опись. Приложение выводит хеши в нижнем регистре; проверяющий код принимает оба регистра.

Элемент `exclusions` имеет три строковых поля:

| Поле | Значение |
| --- | --- |
| `sourceRelativePath` | Безопасный относительный путь исключённого источника. |
| `archivePath` | Планировавшийся относительный путь копии. |
| `reason` | Непустая причина исключения. Планировщик ограничивает её 4096 символами. |

Содержимое исключённых файлов не копируется, их длины и хеши не записываются. Причина сохраняется в JSON как текст; для строки в `contents.txt` символы CR и LF заменяются пробелами. Исключения не подтверждают существование или содержимое соответствующих исходников у получателя. Лимит 4096 символов применяется при планировании записи; проверяющий код требует непустую причину и ограничивает общий размер описи.

Сам `handinpack.json` не содержит собственного хеша. Проверка `contents.txt` сверяет его байты с длиной и хешем в JSON, но не разбирает текстовую опись заново и не доказывает смысловое соответствие текста массиву `files`.

## Пути и совпадения имён

В описи разрешены относительные пути с `/`. Планировщик заменяет введённые `\` на `/`; готовая опись и имена записей ZIP должны уже использовать `/`.

Запрещены абсолютные пути, пустые сегменты, `.` и `..`, завершающий пробел или точка в сегменте, управляющие символы ниже U+0020 и символы `< > : " | ? *`. Двоеточие не допускается и для альтернативных потоков NTFS. Отдельный сегмент не длиннее 255, весь путь не длиннее 32 000 кодовых единиц UTF-16. Ограничения конкретной файловой системы и итогового полного пути могут быть строже.

Отклоняются зарезервированные имена Windows, включая `CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `COM1`-`COM9`, `LPT1`-`LPT9` и варианты с надстрочными цифрами ¹, ², ³. Расширение не делает такое имя допустимым.

Для сравнения путей используется нормализация Unicode NFC с последующим `ToUpperInvariant`. Исходное написание допустимого пути сохраняется. Поэтому `report.pdf` и `REPORT.PDF`, а также канонически эквивалентные записи Unicode не считаются разными файлами. Разные написания одной промежуточной папки тоже отклоняются. Один путь нельзя одновременно использовать как файл и как родительский каталог другого файла.

Расширения в пользовательских требованиях сравниваются без учёта регистра и проверяются по итоговому имени. Это не проверка типа содержимого. Обязательные пути проверяются по тем же ключам имён; исключённый файл не выполняет требование.

## Запись и проверка байт

Запись проходит последовательность:

```text
проверка плана -> новая .incomplete запись -> копирование и SHA-256
-> обе описи -> повторное чтение результата -> итоговое имя
```

Файлы обрабатываются по одному, в порядке `archivePath` с порядковым сравнением строк. Для чтения, записи и хеширования используется буфер 128 КиБ из пула. SHA-256 рассчитывается по байтам, прочитанным из исходника и переданным в копию. ZIP использует сжатие `CompressionLevel.Optimal` стандартной библиотеки .NET, без шифрования.

Для каждого открытого исходника сверяются атрибуты неподдерживаемого типа, длина и время последнего изменения с данными сканирования, до и после копирования. Обычное изменение размера или времени после сканирования останавливает сборку. Это не сохранённый хеш исходника на момент сканирования.

После записи проверяются:

- Наличие обеих описей, допустимость JSON и путей, отсутствие неоднозначных имён.
- Соответствие полного набора файлов описи, без пропущенных или лишних файлов.
- Точная длина и SHA-256 каждого включённого файла и `contents.txt`.
- Для папки - отсутствие лишних каталогов, не являющихся родителями включённых файлов.
- Отсутствие поддерживаемых проверкой признаков ссылок и облачных заполнителей.

ZIP проверяется без распаковки на диск. Записи со ссылочными атрибутами отклоняются. Файловая проверка не исправляет результат.

Итоговый объект появляется через перенос промежуточной записи в той же родительской папке, без замены существующего пути. Это не обещание транзакции при потере питания. При ошибке или отмене промежуточная запись может остаться; автоматического возобновления и автоматической очистки нет. Если ошибка возникла до создания записи, промежуточного объекта может не быть.

## Размеры

| Значение | Что считается |
| --- | --- |
| Размер одного файла | Длина его основного потока байт до сжатия. |
| Размер материалов | Сумма длин включённых файлов, без исключений и служебных описей. |
| Размер результата ZIP | Длина всего файла ZIP после закрытия архива, включая сжатые описи и структуру ZIP. |
| Размер результата-папки | Сумма длин включённых файлов, `handinpack.json` и `contents.txt`. Не занимаемое место по кластерам и не размер метаданных файловой системы. |

Лимит готового результата проверяется после записи, поэтому не является предварительным резервированием места на диске. В интерфейсе положительные дробные МиБ переводятся в байты с округлением вниз; пустое поле означает отсутствие пользовательского лимита. В API и рецепте лимиты хранятся в байтах, `null` означает отсутствие ограничения. Core принимает нулевой лимит; интерфейс для непустого поля требует положительное число.

Копируются байты основного потока файла. Приложение не переносит ACL, владельцев, альтернативные потоки, исходные атрибуты и временные метки как контракт резервного копирования. Встроенные метаданные внутри самих байт, например EXIF изображения, не удаляются.

## Локальный рецепт

Файл `.handinpack.json`, сохранённый кнопкой **«Сохранить набор»**, отличается от машинной описи `handinpack.json` внутри результата. Это локальный план повторной сборки, а не проверенный комплект.

| Поле рецепта | Содержание |
| --- | --- |
| `version` | `1`. |
| `packageName` | Имя будущего результата. |
| `destinationDirectory` | Локальная папка назначения. |
| `format` | Числовое значение: `0` для папки, `1` для ZIP. |
| `rules` | Требования к составу и размерам. |
| `sourcePaths` | Массив абсолютных локальных путей добавленных корней. |
| `edits` | Массив сохранённых решений для исходных файлов. |

`rules` содержит `allowedExtensions` и `requiredPaths` - массивы строк, а также `maxFileBytes`, `maxTotalBytes`, `maxOutputBytes` - целые 64-битные числа или `null`. Элемент `edits` содержит `sourcePath`, `archivePath`, `included` и `exclusionReason`; причина может быть `null` для включённой позиции.

При открытии рецепта исходники перечитываются. Сохранённые решения сопоставляются по абсолютному `sourcePath` без учёта регистра. Исчезнувшие позиции не создаются из рецепта, новые файлы исходных папок сканируются заново. Поэтому рецепт не заменяет сохранённый комплект и не гарантирует прежний состав.

Рецепт ограничен 16 МиБ и глубиной JSON 24; при сохранении и чтении допускается до 10 000 корневых путей. Неизвестные и повторяющиеся JSON-свойства отклоняются. Сохранение создаёт новый файл через промежуточный `.handinpack-recipe-<идентификатор>.partial`, без замены существующего рецепта.

Пути источников и непустой путь назначения внутри рецепта проверяются перед автоматическим доступом: требуется обычный абсолютный путь с буквой локального диска. UNC, пространства имён устройств и подключённые сетевые диски отклоняются; существующие компоненты пути не должны иметь признаков reparse point, offline или облачного заполнителя. Эта проверка применяется при сохранении и открытии рецепта. Отсутствующий локальный источник не превращается в сетевой запрос: при сканировании он отображается как недоступный.

Это не утверждение, что приложение никогда не обращается к сети. Системный файловый диалог может обращаться к месту, которое пользователь выбирает явно, в том числе при выборе самого файла рецепта. Прямое добавление сетевых источников через диалог не равно их автоматическому открытию из рецепта и не прошло полный набор проверок. Для версии 0.1 рекомендуются обычные локальные диски.

**Приватность:** рецепт содержит абсолютные пути, которые могут раскрыть имя пользователя и устройство каталогов. Он не добавляется в комплект автоматически, но приложение не предотвращает его ручное включение как обычного файла. Описи готового комплекта содержат относительные имена и причины исключения; произвольный текст причины тоже может раскрывать сведения, введённые пользователем. Приложение не очищает содержимое самих материалов от персональных данных.

## Ограничения

| Ограничение | Порог |
| --- | --- |
| Каждый служебный файл | Не более 16 МиБ; `handinpack.json` не может быть пустым. |
| Включённые файлы в описи | Не более 100 000. |
| Исключения в описи | Не более 100 000. |
| Все материалы | Не более 1 ТиБ = 1 099 511 627 776 байт. |
| Перечисление исходных каталогов | До 200 000 посещённых записей; достижение ограничения формирует ошибку неполного сканирования. |
| Записи ZIP при проверке | Не более 100 002, включая служебные файлы. |
| Файлы и папки результата при проверке | Не более 200 002 посещённых записей. |

Это верхние ограничения, **не гарантия вместимости**. Длинные пути, причины исключения, экранирование текста в JSON и число каталогов могут исчерпать лимит раньше 100 000 файлов. При записи используется также консервативная оценка размера JSON, поэтому отказ возможен до точного достижения 16 МиБ. Доступная память, место, ограничения файловой системы и права доступа действуют независимо.

**ZIP и ресурсы:** стандартный `ZipArchive` разбирает центральный каталог архива до того, как приложение проверит `Entries.Count`. Поэтому лимит записей Handinpack не ограничивает предварительные затраты памяти и времени парсера. Нельзя считать проверку произвольного недоверенного ZIP изолированной или гарантированно ограниченной по ресурсам. Для сомнительных архивов используйте отдельное ограниченное окружение.

Ссылки, junction, reparse points и отмеченные соответствующими атрибутами облачные заполнители не поддерживаются. Обнаруженная внутри папки ссылка исключается без обхода её цели; ссылочный корень или его предок блокирует чтение. Пустые папки не сохраняются. Все проверки конкретных путей остаются зависимыми от семантики Windows и файловой системы.

В тестах есть реальные файловые операции, отмена внутри копирования и проверки, а также повреждение ZIP и описей. Реальное исчерпание места на томе, аварийное отключение питания и запуск на чистой машине без среды разработки не являются подтверждёнными сценариями этих тестов.

## Границы проверки

SHA-256 здесь отвечает на вопрос «совпадают ли записанные байты с этой описью». Он не доказывает авторство, доверенность источника, отсутствие вредоносного содержимого или невозможность подмены самого JSON. Опись не подписана, внешнего доверенного хеша нет. Меняя опись вместе с файлами, можно получить иной комплект, проходящий проверку.

Handinpack не использует VSS и не фиксирует весь каталог на один момент времени. Проверки открытых файлов помогают обнаружить обычные изменения, но не являются защитой от враждебной гонки в файловой системе, подмены путей между проверками или изменения байт с сохранением наблюдаемых метаданных. Перед сборкой остановите запись в исходники. Приложение не заменяет средство резервного копирования, антивирус или цифровую подпись.
